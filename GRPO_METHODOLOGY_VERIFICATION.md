# Verification of GRPO_METHODOLOGY_REPORT.md

Verified on 2026-09-10 against the local Afterburner checkout at `ee3f90e15420aee5ae294683ed7c011a645f7d05`. This matches the revision named in the report. The original report and Afterburner source were left unchanged.

**Verdict: the central implementation account is accurate, but six claims need correction or qualification.** The main reward formula, launcher settings, and both iterative-evaluation defects are supported by the code. This was a source audit with isolated executable checks, not a reproduction of model training or published results.

1. **The correctness transition does not add a baseline-dependent learning signal after group centering.** [Report line 210](</Users/academicweapon/Documents/CodingTypeShii/git-research/probed grpo/GRPO_METHODOLOGY_REPORT.md:210>) calls this denser than candidate-only pass/fail and presents repair as receiving a stronger incentive than preserving correctness. The four raw values are correct, but [the implementation](</Users/academicweapon/Documents/CodingTypeShii/git-research/Afterburner/grpo/afterburner_reward_function.py:110>) is exactly

   `Rc = 1.5 * candidate_passed - 0.5 - 0.5 * baseline_passed`.

   Every candidate in a prompt group shares the same baseline. The baseline-dependent term is therefore a constant removed by group centering. With equal format and efficiency terms, failed-baseline and passed-baseline groups have identical centered rewards for the same candidate pass pattern. The correctness component supplies two outcome levels per prompt; efficiency supplies the finer distinctions among passing candidates. Baseline code and measurements still matter through the prompt and relative efficiency reward. Qualify the repair-bonus interpretation in sections 5.1 and 10 as an interpretation of raw scores, not an additional GRPO advantage. [Upstream group-centering implementation](https://github.com/verl-project/verl/blob/main/verl/trainer/ppo/core_algos.py).

2. **The alleged tilde-path defect is not established.** [Report line 438](</Users/academicweapon/Documents/CodingTypeShii/git-research/probed grpo/GRPO_METHODOLOGY_REPORT.md:438>) stops its analysis at `os.path.join`. The path is actually passed to [Dataset.to_parquet](</Users/academicweapon/Documents/CodingTypeShii/git-research/Afterburner/grpo/afterburner_dataset.py:112>). The upstream writer opens string paths through `fsspec.open`, and fsspec's local filesystem explicitly expands a leading `~`. Consequently, the absence of `os.path.expanduser` in this script does not demonstrate a literal-tilde output directory or export failure. Remove this from the confirmed-defect table unless a particular dependency version reproduces it. Historical dependencies are unpinned, and a complete export was not run. [Datasets writer](https://github.com/huggingface/datasets/blob/main/src/datasets/io/parquet.py), [fsspec path normalization](https://filesystem-spec.readthedocs.io/en/latest/_modules/fsspec/implementations/local.html).

3. **The paper/code reward comparison omits an additional clipping difference.** [Report line 260](</Users/academicweapon/Documents/CodingTypeShii/git-research/probed grpo/GRPO_METHODOLOGY_REPORT.md:260>) uses the same efficiency symbol for the paper and repository after defining it with a clipped gain. The code clips the relative gain to `[-1, 1]` before `tanh`; the paper's Equation 8 clips measurements but does not specify this second clip. With baseline runtime 10 and candidate runtime 30, the implemented efficiency component is about `-0.761594`, while the displayed paper equation gives `-0.964028`. Define separate efficiency expressions and include this difference alongside the coefficient and format-penalty differences. [Code](</Users/academicweapon/Documents/CodingTypeShii/git-research/Afterburner/grpo/afterburner_reward_function.py:94>), [paper Equation 8](https://arxiv.org/html/2505.23387v3#S4.E8).

4. **The format validator does not guarantee well-formed, unique tag pairs.** [Report line 240](</Users/academicweapon/Documents/CodingTypeShii/git-research/probed grpo/GRPO_METHODOLOGY_REPORT.md:240>) describes an exact top-level structure. The regex enforces an outer shape but accepts duplicate closing tags, a `<solution>` block inside the thinking content, and empty content without any code fence. These inputs returned `True` when executed against [the actual function](</Users/academicweapon/Documents/CodingTypeShii/git-research/Afterburner/grpo/afterburner_reward_function.py:117>):

   ```text
   <thinking>x</thinking></thinking><solution>code</solution></solution>
   <thinking><solution>junk</solution></thinking><solution>code</solution>
   <thinking></thinking><solution></solution>
   ```

   Describe it as a permissive regex check. Code extraction and execution are separate checks. The report already notes some parser permissiveness in section 11.2; section 5.3 should reflect it too.

5. **PPO clipping does not bound the actual policy step.** [Report line 323](</Users/academicweapon/Documents/CodingTypeShii/git-research/probed grpo/GRPO_METHODOLOGY_REPORT.md:323>) says clipping limits individual policy steps. Clipping limits the surrogate objective's incentive for certain probability-ratio changes; it does not enforce a hard ratio or KL constraint on the resulting policy. Say that it discourages excessive updates, while large policy changes remain possible. The report correctly identifies both explicit KL penalties as disabled. [PPO explanation and limitation](https://spinningup.openai.com/en/latest/algorithms/ppo.html).

Use absolute local links, or commit-pinned GitHub links for a portable report. The source files and cited code generally exist; the link roots are wrong.
